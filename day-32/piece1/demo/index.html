The BOLA fix, running live, not just in a test suite.

Day 32 of the ParkFlow capstone (ADR-001, day-28/piece1): the reservation-ownership check built across days 29–31 is deployed. Every request below ran against the real URL, in this order, moments before this page was published — not simulated, not replayed from a local run.

Try it https://parkflow-demo-20667.azurewebsites.net — a real browser frontend now sits at that URL: sign in as a demo user, book a spot, run it through Confirm/Check-in/Complete, and watch the charge total update. What follows on this page is the focused request/response proof of the ownership check specifically — the live site is the fuller demo.

The run, step by step

  1. 1

    No credentials at all — the API refuses before it even looks at the route.

    POST /api/v1/reservations/<id>/cancel
    401 Unauthorized
  2. 2

    userA books a spot with a valid API key.

    POST /api/v1/reservations  -H X-Api-Key
    201 Created {"reservationId":"f20a9e69-e296-4063-9549-fdb15e3a50b8"}
  3. 3

    Mint real per-user tokens for userA (the owner) and userB (a stranger).

    POST /api/v1/dev/token  {"user":"userA"} / {"user":"userB"}
    200 OK{"token":"eyJhbGciOi…"}
  4. 4

    userB has a genuinely valid key + token — just not for this reservation.

    POST /api/v1/reservations/f20a9e69…/cancel  -H "Bearer userB"
    403 Forbidden {"error":"You do not own this reservation."}
  5. 5

    userA, the actual owner, cancels it.

    POST /api/v1/reservations/f20a9e69…/cancel  -H "Bearer userA"
    204 No Content
  6. 6

    Cancelling it again is a business-state failure now — not an auth one.

    POST /api/v1/reservations/f20a9e69…/cancel  -H "Bearer userA"
    400 Bad Request
  7. 7

    A reservation that never existed reports 404, distinct from the 403 above.

    POST /api/v1/reservations/99999999…/cancel  -H "Bearer userA"
    404 Not Found {"error":"Reservation not found."}
Why /dev/token answers on a live URL: this deployment runs ASPNETCORE_ENVIRONMENT=Development specifically so step 3 is possible to demo — day-27's threat model documents that same endpoint failing closed (a 404) outside Development everywhere else this app has run. A real launch would use a real identity provider (Build Day 32's stretch goal) instead of trading that control away. See the postmortem for the full reasoning.
